# MedixPro — Migration Guide

How to move the MedixPro project (Django backend + Flutter frontend) to a new
machine, server, or environment and get it running end-to-end.

> For a full description of what the project *is*, see
> [`PROJECT_DOCUMENTATION.md`](./PROJECT_DOCUMENTATION.md). This document is
> only about **migrating / setting up** the two subprojects:
>
> - `medixpro_backend/` — Django 5 + DRF REST API (JWT, SQLite)
> - `medixpro/` — Flutter cross-platform app (BLoC/Clean Architecture)

---

## 0. TL;DR checklist

**Backend**
- [ ] Install Python 3.13 (project was built on **3.13.5**)
- [ ] Recreate the virtualenv — **do not** copy the old `venv/`
- [ ] `pip install -r requirements.txt`
- [ ] Copy `db.sqlite3` **and** the `media/` folder (or run a fresh `migrate`)
- [ ] Set env vars (`DJANGO_SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DOCTOR_SECRET_KEY`, `CORS_ORIGINS`)
- [ ] `python manage.py migrate` then `runserver`

**Frontend**
- [ ] Install Flutter (Dart SDK **^3.9.2**)
- [ ] `flutter pub get`
- [ ] **Edit `lib/core/network/api_client.dart` → `_baseUrl`** to point at the new backend host ⚠️ most common breakage
- [ ] `flutter gen-l10n` (if localization files aren't regenerated automatically)
- [ ] `flutter run` / `flutter build <target>`

---

## 1. What to copy vs. what to regenerate

When moving the repo, **copy the source but regenerate build/dependency artifacts.**

| Path | Action | Why |
|---|---|---|
| `medixpro_backend/` source | ✅ copy | The app code |
| `medixpro_backend/venv/` | ❌ **exclude / recreate** | Virtualenv is machine- & path-specific; committed here by accident |
| `medixpro_backend/db.sqlite3` | ⚠️ copy **if** you want existing data | Otherwise start fresh with `migrate` |
| `medixpro_backend/media/` | ✅ copy | Uploaded files (report PDFs, avatars) live here — lost if not carried over |
| `*.log` (`medixpro.log`, `medixpro_errors.log`) | ❌ exclude | Regenerated at runtime |
| `__pycache__/`, `*.pyc` | ❌ exclude | Regenerated |
| `medixpro/` source (`lib/`, `pubspec.yaml`, `assets/`, platform folders) | ✅ copy | The app code |
| `medixpro/build/`, `medixpro/.dart_tool/` | ❌ exclude / recreate | Build output; regenerated by `flutter pub get` / build |
| `hs_err_pid*.log`, `replay_pid*.log` (repo root) | ❌ delete | JVM crash dumps, not part of the project |
| `.docx` files at root | ➖ optional | Source docs, not needed to run |

A reasonable `.gitignore` (if not already present) should cover:
`venv/`, `__pycache__/`, `*.pyc`, `*.log`, `db.sqlite3`, `medixpro/build/`,
`medixpro/.dart_tool/`, `*.iml`, `.gradle/`.

## 2. Backend migration (`medixpro_backend/`)

### 2.1 Prerequisites

- **Python 3.13** (built on 3.13.5). Django 5.0–5.2 also supports 3.10–3.12 if
  you need an older interpreter.
- `pip` / `venv`.
- (Optional) Redis, **only if** you later wire up Celery — currently unused at runtime.

### 2.2 Set up the environment

```bash
cd medixpro_backend

# Recreate the virtualenv (never copy the old one)
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

pip install --upgrade pip
pip install -r requirements.txt
```

`requirements.txt`:

```
Django>=5.0,<5.2
djangorestframework
djangorestframework-simplejwt
django-cors-headers
Pillow
celery
redis
cryptography>=42        # AES-GCM / JWE for the Sham Cash payment integration
requests>=2.31          # HTTP client for Sham Cash API calls
```

> `cryptography` and `requests` are **required** by the `payments` app (Sham Cash
> booking fees) — the backend will not import without them.
>
> `celery` and `redis` are installed but **not wired into settings** — no broker
> is configured, so they don't need to be running. They can stay in
> requirements without affecting the migration.

### 2.3 Environment variables

Settings read these from the environment, all with **insecure fallback
defaults**. Set them explicitly on the new host (especially for anything public):

| Variable | Default (fallback) | Notes |
|---|---|---|
| `DJANGO_SECRET_KEY` | `change-me-in-production` | **Set a real secret** before exposing the server |
| `DEBUG` | `True` | Set to `False` in production |
| `ALLOWED_HOSTS` | `*` | Comma-separated; restrict in production |
| `DOCTOR_SECRET_KEY` | `MEDIX-DOCTOR-2026` | Gate for doctor self-registration; clients must send the same value |
| `CORS_ORIGINS` | `http://localhost:8000` | Comma-separated allowed origins (used only when `DEBUG=False`, since `CORS_ALLOW_ALL_ORIGINS = DEBUG`) |
| `SHAMCASH_BASE_URL` | `https://dev.shamlogix.tech/services` | Sham Cash E-Payment API root |
| `SHAMCASH_AGENT_KEY` | `JKAWASLaflka1351FLPG` | Sham Cash agent identifier |
| `SHAMCASH_SECRET_KEY` | *(dev key baked in)* | **Base64 of 32 bytes** (AES key). **Rotate for production**; server-side only |
| `SHAMCASH_CURRENCY_ID` | `2` | Currency for fees: `1`=USD, `2`=SYP |
| `PLATFORM_FEE_RATE` | `0.20` | Booking fee = this fraction of the doctor's receipt |
| `PUBLIC_BASE_URL` | `http://127.0.0.1:8000` | Publicly reachable backend URL for Sham Cash `callbackUrl`/`redirectUrl` — **see §3.6** |

> The Sham Cash dev credentials ship as fallback defaults so local testing works
> out of the box. For production, set real values — especially rotate
> `SHAMCASH_SECRET_KEY`, which authorises the whole agent account and must never
> reach the Flutter client. Full details: `PAYMENTS_INTEGRATION.md`.

Example `.env`-style export (there is **no** `.env` loader wired in — export in
the shell, systemd unit, or container env):

```bash
export DJANGO_SECRET_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(50))')"
export DEBUG=False
export ALLOWED_HOSTS="api.example.com,10.0.0.5"
export DOCTOR_SECRET_KEY="choose-a-new-doctor-key"
export CORS_ORIGINS="https://app.example.com"
```

> ⚠️ If you change `DOCTOR_SECRET_KEY`, doctors registering from the Flutter app
> must supply the new value at the "verify doctor key" step, or registration fails.

### 2.4 Database

The project uses **SQLite** (`DATABASES → BASE_DIR / "db.sqlite3"`). Choose one:

**Option A — carry existing data (recommended for a like-for-like move)**
1. Copy `db.sqlite3` into `medixpro_backend/`.
2. Copy the `media/` folder too (DB rows reference files there).
3. Apply any new migrations:
   ```bash
   python manage.py migrate
   ```

**Option B — fresh database**
```bash
python manage.py migrate
python manage.py createsuperuser   # optional, for /admin
```

**Option C — data only, portable across DB engines (e.g. moving to Postgres)**
```bash
# On the old machine:
python manage.py dumpdata --natural-foreign --natural-primary \
  -e contenttypes -e auth.permission > data.json
# On the new machine, after configuring the DB and running migrate:
python manage.py loaddata data.json
```

Migration counts present in the repo (all must apply cleanly):
`users:4`, `patients:4`, `appointments:5`, `medications:3`, `notifications:1`,
`reports:3`, `payments:1`. `core` and `dashboard` define no models.

> The `payments` app (Sham Cash booking fees) adds `Payment`, `PayoutSettlement`,
> and `WebhookEvent`; `users:0004` adds `Profile.receipt_amount`; `appointments:0005`
> adds `AppointmentRequest.awaiting_payment` and `Appointment.completed_at`. These
> ship as ordinary migrations — a fresh `migrate` (Option B) creates them all.

### 2.5 Run

```bash
python manage.py runserver 0.0.0.0:8000
```

- API base path: `/api/v1/` (e.g. `http://<host>:8000/api/v1/auth/login/`).
- Django admin: `http://<host>:8000/admin/`.
- Bind to `0.0.0.0` (not the default `127.0.0.1`) if the Flutter app runs on a
  **different device** (emulator or phone) — otherwise it can't reach the server.

### 2.6 Production serving (optional)

For a real deployment, run under a WSGI server behind a reverse proxy:

```bash
pip install gunicorn
gunicorn medixpro_backend.wsgi:application --bind 0.0.0.0:8000
```

Serve `media/` and `static/` via the reverse proxy (nginx) or WhiteNoise — see
the known-issues section, since static/media settings need fixing first.

## 3. Known migration gotchas ⚠️

These are pre-existing issues that bite specifically **during a move to a new
environment**. Address them as part of migration.

### 3.1 Flutter API base URL is hardcoded — **fix this first**

`medixpro/lib/core/network/api_client.dart`:

```dart
static const _baseUrl = "http://127.0.0.1:8000/api/v1/";
```

`127.0.0.1` only works when the app runs on the **same machine** as the backend
(e.g. Flutter desktop/web on localhost). After migrating, set it to match how
the client reaches the server:

| Client target | Use |
|---|---|
| Android **emulator** → host machine | `http://10.0.2.2:8000/api/v1/` |
| iOS **simulator** → host machine | `http://127.0.0.1:8000/api/v1/` |
| Physical device / another machine | `http://<server-LAN-IP>:8000/api/v1/` |
| Production | `https://<your-domain>/api/v1/` |

There are already commented example URLs in that file to swap in. Consider making
this configurable via `--dart-define` instead of a hardcoded constant.

### 3.2 `MEDIA_ROOT` / `MEDIA_URL` / `STATIC_ROOT` — now configured ✅

Previously undefined; **fixed** in `settings.py` (the payment work needed proper
media/static config). It now sets:

```python
STATIC_ROOT = BASE_DIR / "staticfiles"   # for `collectstatic` in production
MEDIA_URL   = "/media/"
MEDIA_ROOT  = BASE_DIR / "media"
```

For a production deployment, run `python manage.py collectstatic` and serve
`media/` + `static/` via the reverse proxy. No action needed for a dev migration.

### 3.3 `dashboard` app is not in `INSTALLED_APPS`

The `dashboard/` views are imported and routed directly from the root `urls.py`,
but `dashboard` is **not** listed in `INSTALLED_APPS`. It works today only
because the app defines no models. If you add models to it later, add
`"dashboard"` to `INSTALLED_APPS` and create migrations.

### 3.4 Insecure default secrets

`DJANGO_SECRET_KEY` (`change-me-in-production`), `ALLOWED_HOSTS` (`*`), and
`DOCTOR_SECRET_KEY` (`MEDIX-DOCTOR-2026`) fall back to insecure values. Set real
ones (§2.3) before exposing the backend.

### 3.5 Android application id is still the default

`medixpro/android/app/build.gradle.kts` uses `applicationId =
"com.example.medixpro"`. Change it to a real package id before publishing to a
store; changing it after release is a breaking change for existing installs.

### 3.6 Sham Cash payments need a public URL + a custom User-Agent

The `payments` app (booking fees) calls the Sham Cash gateway and receives an
async webhook. Two things bite after a move:

- **`PUBLIC_BASE_URL` must be publicly reachable.** It builds the `callbackUrl`
  (webhook) and `redirectUrl` sent to Sham Cash. On `localhost`, Sham Cash cannot
  deliver the "Paid" webhook, so a paid bill stays `pending` until the ~10-minute
  `getBillInfo` fallback fires. For local end-to-end testing, tunnel the backend
  (e.g. `ngrok http 8000`) and set `PUBLIC_BASE_URL` to the tunnel URL.
- **User-Agent gotcha (already handled in code):** the gateway's WAF returns
  `HTTP 403 "banned permanently"` for the default `python-requests` User-Agent.
  The client sends `User-Agent: MedixPro-Agent/1.0` to avoid it — don't remove it.

Full integration reference: `PAYMENTS_INTEGRATION.md`.

## 4. Frontend migration (`medixpro/`)

### 4.1 Prerequisites

- **Flutter SDK** with Dart **^3.9.2** (`flutter --version`).
- Platform toolchains for whichever targets you build:
  - Android: Android SDK + a device/emulator
  - iOS/macOS: Xcode (macOS host only)
  - Web: Chrome
  - Linux/Windows: desktop build deps
- Run `flutter doctor` and resolve anything flagged for your target.

### 4.2 Set up

```bash
cd medixpro
flutter pub get
```

If localization sources changed or aren't generated, regenerate them
(driven by `l10n.yaml` from `lib/l10n/app_en.arb` / `app_ar.arb`):

```bash
flutter gen-l10n
```

### 4.3 Point the app at the backend

Edit `lib/core/network/api_client.dart` → `_baseUrl` (see §3.1). **This is the
single most common cause of "app runs but every request fails" after a move.**

### 4.4 Run / build

```bash
flutter run                       # pick a connected device
# or build a release artifact:
flutter build apk                 # Android
flutter build appbundle           # Android (Play Store)
flutter build ios                 # iOS (macOS host)
flutter build web                 # Web
flutter build linux | macos | windows
```

Assets referenced from `pubspec.yaml` (e.g. `assets/animations`) are bundled
automatically — ensure the `assets/` folder was copied.

## 5. Post-migration smoke test

1. **Backend up:** `curl http://<host>:8000/api/v1/` (or open `/admin/`).
2. **Auth works:** register/login via the app, confirm a JWT is returned.
   - If doctor registration fails → check `DOCTOR_SECRET_KEY` matches on both sides (§3.1/§2.3).
   - If every request fails with a network/CORS error → check `_baseUrl` (§3.1) and `CORS_ORIGINS`/`DEBUG` (§2.3).
3. **Data present:** patients/appointments lists load (confirms DB + media moved).
4. **File uploads:** open a report with an attachment / a profile avatar
   (confirms `media/` moved and media settings resolve — §3.2).
5. **Localization:** toggle English/Arabic in the app.
6. **Payments (optional, needs public `PUBLIC_BASE_URL`):** as a patient, open
   "New Request", pick a doctor, tap **Book & Pay**, and confirm the Sham Cash
   checkout opens. A quick server-side sanity check that the gateway handshake
   works: `cd medixpro_backend && ./venv/bin/python manage.py test payments`.
